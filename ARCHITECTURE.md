# Supply Chain Guardian architecture

The revised architecture diagrams supplied on November 24, 2026 define the target. Existing Python discovery, detection, evidence storage, and vanilla JavaScript views remain in use. This document distinguishes implemented behavior from planned modules.

## Central orchestration

`guardian/orchestrator.py` coordinates the ordered modules `discover`, `detect`, `analyze`, `remediate`, and `validate`. `guardian/app.py` submits orchestration to the existing single-worker executor. Discovery-only and detection-only API routes remain compatible with saved scans and the current dashboard.

SQLite at `data/scans/guardian.sqlite3` uses schema version 2 for jobs, module attempts, events, cancellation, AI request counters, rate reservations, cooldowns, and validated explanation caching. Version 1 databases gain additive tables without resetting jobs or budgets. JSON artifacts remain in each scan directory. Stage checkpoints contain SHA-256 hashes, repository commit, completion status, and timestamp. The database is authoritative for execution state; a checkpoint is reusable only when the database records a usable module outcome and all checkpoint artifact hashes still match.

The worker runs all five modules. Remediation creates proposals; validation pauses at `awaiting_approval` until every exact diff has an immutable approve/reject/accepted-risk review. Workflow completion is separate from security verification. Legacy `/api/scans/{id}` status describes discovery; `/api/scans/{id}/pipeline` describes the entire pipeline.

Jobs transition from `queued` to `running`, then to `blocked`, `completed`, `failed`, or `cancelled`. Cancellation during execution passes through `cancelling`. Restart converts active jobs to `interrupted`; resumption is explicit. Resume reuses valid completed, incomplete, or partial modules. It reruns a missing or modified checkpoint and invalidates downstream module state. No automatic unbounded retry occurs. Existing OSV/tool retry and timeout bounds remain unchanged.

Cancellation is cooperative at stage callbacks, subprocess polling, and OSV request/response boundaries. Tool cancellation kills the child process group. An in-flight HTTP request can wait until its existing timeout before cancellation is observed. Partial output may persist without a reusable checkpoint. Queue capacity remains one running job and two queued jobs across discovery, detection, and orchestration. Use one server process.

## Module mapping

| Module | Existing implementation | Remaining work |
| --- | --- | --- |
| Discover | Restricted public GitHub intake, pinned checkout, npm lockfiles/manifests, Python declarations, trust tiers, separate deps.dev inference, directed graph, Syft SBOM | Additional lockfile formats remain detect-only |
| Detect | Exact-version OSV with separate MAL labels, withdrawal/alias checks, lifecycle flags and registry scripts, offline typosquat signals, local policy, baseline change rules, workflow/Dockerfile checks | Additional advisory ecosystems and package-manager policy adapters remain unsupported |
| Analyze | JS/TS package import observations, deterministic priorities/CVSS parsing, evidence confidence, gateway explanations and signal review | Function-level exploitability and non-JS source models remain outside scope |
| Remediate | No implementation | OSV-checked candidate versions, safe npm lock regeneration, deterministic patch and rollback plan |
| Validate | No implementation | Explicit diff approval, isolated rebuild, optional sandboxed tests, rescan and before/after comparison |

Milestone 2 adds Python parsing for `requirements.txt` and standard `[project]` dependencies and optional dependencies in `pyproject.toml`. Multiple supported Python manifests in one directory share one application. Markers and extras remain literal declarations; they are not evaluated against the scanner's host. Includes, pip options, editable inputs, dynamic dependencies, and legacy tool metadata are not executed or followed. Poetry and uv locks, as well as Yarn and pnpm locks, remain detect-only. npm retains its existing v2/v3 lockfile parser and workspace handling.

## Discovery trust and routing

Supported npm locks use the exact recorded topology and retain `verified_lockfile` package observations. Without a lock, supported npm and Python manifests preserve literal declarations. An exact pin yields `declared_exact` and a separate `declared_version`; it never fills `version` or `resolved_version`. An unresolved constraint yields `constraint_only`, while missing package version evidence yields `unknown`.

`guardian/depsdev.py` infers possible graphs for up to twenty direct declarations across a scan. It chooses the highest indexed version satisfying an npm range through `semantic-version.NpmSpec` or a Python requirement through `packaging`. Python prerelease selection uses `SpecifierSet.filter`. Unsupported npm references and Python URL, marker, or extra requirements remain declaration-only. No dependency resolver, package installation, build backend, or repository code runs. Independent package graphs do not establish a joint project resolution, peer agreement, selected extras, or platform compatibility.

Inferred versions go only into `inferred_version`. Transitive inferred nodes have `resolution_status: inferred` and `trust_tier: externally_inferred`. An exact direct declaration retains `declared_exact` even when it has an external graph; its inference is shown separately. Direct non-exact declarations with a successfully inferred graph become `externally_inferred`. Actual lockfile versions and topology are never overwritten.

Graph JSON exports verified edges as `edges`, declarations as `declared`, and external relationships as `inferred`. Observed paths and direct/transitive classifications can traverse declarations and inference. Verified per-project reachability and advisory path correlation use resolved edges only. Project filtering includes each project's complete observed subgraph, including cycles and transitive inferred nodes. The dashboard shows inferred node labels, dashed inference edges, accessible descriptions, and a separate trust/version table.

The deps.dev client contacts only `https://api.deps.dev` package-version and dependency-graph endpoints. It ignores advisory fields and never calls deps.dev advisory endpoints. It has a thirty-second scan-wide inference budget, forty requests, eight-second request timeouts, four MiB per response, sixteen MiB total response bytes, ten thousand indexed versions per package, three thousand nodes and ten thousand edges per returned graph. Existing combined inventory bounds still apply. It does not follow redirects or read environment credentials. A 429, 5xx, transport failure, or byte-limit failure stops further service calls for that scan; there is no automatic retry. Valid responses can be reused in memory within that scan.

Raw response bytes, source URLs, timestamps, commit, and SHA-256 hashes live in `artifacts/discovery/evidence/`. Inventory `inference_evidence` references exact response pointers. These records are separate from detection evidence and are covered by discovery checkpoints. Provider errors retain original declarations and partial coverage. The original Syft SBOM remains unchanged; reconciliation separately lists declared and inferred instances, never promoting a Syft identity to installed evidence.

Official implementation references: [deps.dev API v3](https://docs.deps.dev/api/v3/), [Python requirement parsing](https://packaging.pypa.io/en/stable/requirements.html), [pyproject.toml specification](https://packaging.python.org/en/latest/specifications/pyproject-toml/), and [semantic-version NpmSpec](https://python-semanticversion.readthedocs.io/en/latest/reference.html#semantic_version.NpmSpec).

## Detection and policy

Milestone 3 adds `guardian/signals.py` alongside the existing OSV and Git-comparison detectors. Detection runs these three independent functions against one thread-safe evidence store. Discovery artifacts remain unchanged. The new `static_signals.json` contains inspections, confidence-ranked name signals, script observations, policy outcomes, metadata request counts, and comparison snapshot provenance. The combined detection report retains distinct finding types: `vulnerability`, `suspicious_change`, `install_script`, `typosquat`, and `policy_violation`.

OSV remains the only advisory matching source. Any correlated advisory group containing a `MAL-` identifier is labeled `advisory_category: malicious_package`, with separate verified counts and a dashboard filter. Ordinary CVE/GHSA matches remain vulnerability advisories. Withdrawn records are excluded before classification. Raw advisory severity and exact-version verification remain unchanged. Script patterns, popularity metadata, and name similarity never create an advisory match.

Current repository npm lifecycle commands are inspected without a baseline. For dependency lockfile `hasInstallScript` flags, the detector corroborates source hashes and exact component name/version, then requests only that version's npm registry metadata. It inspects `preinstall`, `install`, `postinstall`, and `prepare` and records bounded regex observations for download/execute chains, dynamic code, encoded payloads, and credential-access strings. Scripts, tarballs, referenced URLs, and package build commands never execute. A script's presence, or a regex match, is not a malware conclusion. Registry metadata can omit implicit native-build behavior or differ from tarball content; missing inspectable commands remain unreviewed.

`policy.yaml` belongs to Guardian, not the scanned repository. Its schema requires explicit `no_git_dependencies` and `no_unreviewed_install_scripts` booleans. Git references in supported npm declarations, lockfile source/version references, and parsed Python URL requirements create source-backed policy findings. Script reviews match an exact command SHA-256 plus repository-relative manifest/lifecycle or dependency name/version/lifecycle. No dependency is implicitly trusted because it is popular. Invalid configuration yields `not_run` and an error; unknown coverage never becomes a policy pass. A policy violation can coexist with successful detection: `policy_status` describes compliance, while detector `status` describes whether inspection completed.

The offline typo detector uses the first 1,000 names from `wooorm/npm-high-impact`'s `npmTopDownloads` list, pinned to commit `9e29478332833af97b0e96801a5187cfd3c28382`. The collected JSON includes its collection timestamp, immutable source URL, upstream byte hash, and method. Its complete local SHA-256 is `8370f55b39946fb727b6e4d4720bb5a621f39ac2119ddb6e240a360a0ca8e7dd`; runtime checks verify this hash before use. The upstream MIT license is retained. This is an upstream-ordered historical comparison list, not a live global ranking or a trusted-package allowlist.

Name checks cover one insertion, deletion, substitution, or adjacent transposition, skip short names and exact snapshot matches, and do not compare across npm scopes. They use deletion indexes rather than comparing every package with every corpus name. The detector caps inspection at 2,000 package names and enriches up to ten suspected names. Optional deps.dev metadata supplies earliest indexed publication timestamps and associated repository stars. Indexed history is not confirmed package creation age; repository stars are not download counts, and project mappings can be unverified. Missing metadata remains explicit and leaves a lower-confidence offline signal. Confidence is a review-order heuristic, never a malware probability or security score.

`guardian/metadata.py` contacts only `registry.npmjs.org` and `api.deps.dev`, with forty-five seconds and sixty total requests per scan, eight-second request timeouts, two MiB per response, and ten MiB total bytes. It performs no redirects or automatic retries and reads no environment credentials. A 429/5xx or transport failure disables that host for the rest of the scan. At most thirty flagged dependency versions receive registry inspection. Current source inspection is capped at 150 npm metadata files. Raw bodies, failed responses, source URLs, retrieval timestamps, and hashes join the existing detection evidence store. deps.dev advisory fields are ignored.

Detection checkpoints now require `static_signals.json`, the detector version, and the exact policy hash used during that detection. Changing local policy invalidates detection reuse while preserving a valid discovery checkpoint. The dashboard exposes separate finding filters, MAL counts, policy status, review confidence, and raw evidence buttons.

References: [npm registry API](https://github.com/npm/registry/blob/main/docs/REGISTRY-API.md), [npm lockfile flags](https://docs.npmjs.com/cli/v11/configuring-npm/package-lock-json/), and [pinned popularity dataset](https://github.com/wooorm/npm-high-impact/tree/9e29478332833af97b0e96801a5187cfd3c28382).

## Package analysis and AI gateway

`guardian/reachability.py` lexically extracts literal JS/TS imports, re-exports, require calls, and literal dynamic imports while skipping comments and quoted text. It binds imports through project declarations and aliases. Verified direct bindings can be `reachable`; transitives inherit `possibly_reachable` through verified directed edges, including cycles. Type-only/test imports, declared-only bindings, dynamic loaders, unresolved alias configuration, absent source, and unsupported ecosystems retain uncertainty. `not_reachable` means no import path was observed within a complete supported static scope, not that runtime loading is impossible. Scanning all source files does not prove application entrypoint or function-level exploitability.

Inspection is bounded to 2,000 source files, ten MiB total, 512 KiB per file, 20,000 import observations, and twenty witnesses per component. Common build/cache/vendor directories are excluded. Source bytes/hashes and lexical observations live under `analysis/evidence/`. Direct witnesses identify file/line; inherited witnesses retain dependency-parent references without materializing every path.

`guardian/analysis.py` validates original finding evidence, preserves discovery/detection artifacts, and calculates deterministic priorities. Advisory labels and CVSS v2/v3/v4 vectors supply severity without overwriting source severity. Scores combine severity/type base, package reachability, component policy signals, explicitly advisory-reported exploitation when supplied, verification strength, and heuristic confidence. Missing exploitation evidence remains `not_supplied`. Scores/confidence are review heuristics, not CVSS replacements or probabilities. Findings retain auditable factors.

All three AI task interfaces share one gateway: explain top findings, review non-CVE signals, and explain deterministic remediation options. Analysis runs the first two tasks; remediation runs fix notes from actual deterministic recommendation options. The flow is compact allowlisted JSON, compatible cache lookup, atomic budget/rate reservation, project-aware Gemini routing, optional local provider, schema validation with one bounded repair, then validated caching or labeled template fallback.

Four key slots match the user's four projects. The illustration's five-key wording does not add a fifth required key. Distinct labels represent operator-configured independent quota groups; missing or repeated labels share a group. Duplicate key values are deduplicated. A 429 persistently cools down that group and cannot be bypassed by changing its credentials or models. Provider rules and configured quotas remain binding. Metadata checks occur only on demand and never prove generation access, billing eligibility, or remaining quota.

Defaults are three attempts per scan, thirty requests per UTC day, and twelve seconds between requests. Failed/fallback/repair attempts consume budget, which can stop routing before every key or local provider is attempted. No keys are configured here, so live verification used templates. Provider routing, repair, local fallback, and cache replay were tested with synthetic transports. AI receives validated IDs and deterministic categories, never source text or commands. Output remains untrusted interpretation and cannot change findings or scores. See `AI_GATEWAY.md` for configuration and model-access details.

Analysis writes `analysis_report.json`, `reachability.json`, `risk_scores.json`, `ai_notes.json`, and separate source evidence. Checkpoints cover these outputs and analysis/configuration versions. The API marks analysis stale after detection changes. The dashboard exposes analysis controls, score factors, import evidence, note provenance, usage, and safe key/model status. Original evidence exports remain unchanged.

## Evidence and trust boundaries

Source bytes, hashes, timestamps, advisory provenance, and finding identifiers remain in the existing evidence store. Discovery checkpoints cover inventory, graph, report, and an SBOM when present. Detection checkpoints also cover raw evidence files. Unknown discovery, incomplete detection, heuristic signals, and AI notes must remain distinct throughout later modules.

Repository installation scripts never execute during discovery or detection. Patch generation uses isolated manifests, fixed registry, sanitized npm configuration, and `--ignore-scripts`. Untrusted build/test commands require appropriate Docker isolation; unavailable isolation produces `not_run`. Validation approval belongs to the application workflow and cannot be inferred from permission to build Guardian.

## Remediation and validation

`guardian/remediation.py` reads fresh analyzed findings and validates original evidence. It checks at most five fixed-version candidates per package against fixed npm metadata and exact OSV queries. Active advisories can supply additional fixed events; an incomplete query or unknown candidate fails closed. Patches support independent npm v2/v3 direct dependencies with unchanged runtime dependency declarations. Other strategies and unsupported projects remain manual recommendations. Regeneration uses an offline temporary manifest/lock pair, script suppression, a fixed registry, empty configurations, sanitized environment, and strict reference preflight. No repository .npmrc is loaded.

Each proposal binds the source snapshot, before/after file hashes, exact diff, candidate evidence, constraints, rollback, and tool record into a digest. SQLite schema 3 adds immutable remediation_reviews while retaining jobs and AI state. Review requires that digest; approving requires reviewed_diff=true. Accepted risk requires a reason and never resolves a finding. Source, detection, analysis, candidate evidence, or patch changes invalidate use. Reviews are local explicit acknowledgements, not authenticated human identities or signed attestations.

`guardian/validation.py` copies bounded regular source files into a temporary derived snapshot, excludes credentials/tool configuration, applies exact approved bytes, and runs npm ci with scripts disabled. Every locked package needs a fixed registry URL and integrity hash. Requested build/test commands require a preloaded digest-pinned Docker image; network, host secrets, write access to source, elevated privileges and image pulls are unavailable. Missing Docker tests remain not_run. Host npm processing is application-isolated, not an OS sandbox.

Discovery/Syft and detection run again against the derived snapshot. Original base commit and patch digest describe provenance; no new Git commit is invented. Component/SBOM identities and findings are compared, including repository-level signals without component IDs. New vulnerabilities and unresolved targets fail validation; missing coverage or tests leaves partial. Each proposal validates independently, never as a combined patch. Raw after-scan artifacts remain under validation/<result> and have API exports. The report includes original analysis notes, fix notes, total AI requests, review audit, remaining manual recommendations, and accurate fully_verified status.

Remediation and validation checkpoints hash their reports, raw evidence and proposal/after-scan artifacts. Validation checkpoints also bind review records. Cancellation remains cooperative between bounded tools and requests. Pending reviews survive restart. UI controls expose preparation, diff inspection, decisions, validation summaries, provenance and downloads; milestone 6 organizes these controls into the six-view workspace.

## Six-view workspace and controlled demo

The frontend remains dependency-free vanilla JavaScript. workspace.js owns route/hash navigation, scan selection, bounded polling, history, real orchestrator state, summaries, exports, and safe settings. Existing graph, detection, analysis and remediation modules keep their evidence contracts. A selected scan has one generation; stale asynchronous results are ignored. Module controls defer to the active orchestrator, and API worker ownership remains authoritative. The overview separates original advisory counts, workflow completion and validation status.

The HTML/CSS design uses a fixed desktop navigation rail, six named views, grouped evidence inspectors, responsive phone navigation, focus rings, and reduced-motion handling. Dark tokens separate canvas/surface/border/text, violet interpretation and cyan evidence. SVG relationships and text-based gateway stages remain code-native and accessible. No chart or metric is fabricated to fill an empty state.

GET /api/scans lists up to 100 local scan summaries. GET /api/scans/{id}/summary reads available reports without triggering a provider and marks changed plans/validation stale. Artifact exports retain original bytes. POST /api/demo creates only fixture://guardian-controlled-demo; regular GitHub intake still rejects that scheme and local paths. demo.py creates fixed manifest/lock/source/sentinel bytes and uses analyze_repository within the ordinary orchestrator. It pauses before approval, preserves immutable decisions, resumes validation with an optional Docker-test request, and never changes the source checkout.

The demo CLI can warm real gateway caches from saved analysis/reachability/remediation payloads. It uses configured providers and ordinary scan/daily budgets. Compatible cache hits need no generation; templates are never inserted as provider-cache results. With no keys, the demo is functional through labeled deterministic notes. UI report replay itself is read-only and makes no generation request.

The optional browser_smoke.cjs harness creates a new fixed controlled fixture, verifies the unchecked-approval guard, records an explicitly automated fixture-only review, resumes validation, and checks six views, mobile overflow, exports, settings and JavaScript errors. It refuses non-loopback targets and asserts controlled-fixture identity before approval. Playwright is a separate QA dependency, not application runtime code.

Design references were generated with the built-in image tool: a complete charcoal/violet/cyan overview and a coordinated diff/review state. Implementation comparison checked rail geometry, palette, typography, spacing, inspector structure and copy. Actual provenance, dates, constraints, manual signals and truthful AI boundaries replace illustrative concept content. Native browser screenshots were inspected at their full saved dimensions; mobile uses a deliberate navigation collapse rather than shrinking desktop text.
